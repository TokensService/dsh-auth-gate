# txt 批量导入用户：本地/服务端双模式与固定 imports/ 沙箱（2026-09-14）

## 决定了什么

用户管理页新增批量导入：`POST /auth/users/import` 接受 `{text}`（本地文件原文，
浏览器 FileReader 读取后随请求提交）或 `{file}`（服务端文件名）二选一。服务端
文件模式只允许读 `<users.yaml 目录>/imports/` 下的 `.txt`（文件名白名单
`SERVER_FILE_RE` 拒绝任何路径分隔符），`GET /auth/users/import` 列出该目录的
候选文件。逐行解析 `用户名,密码`（首个逗号切分、空行与 `#` 注释跳过），全量
校验、失败按行号回报、原子写入（all-or-nothing）。仅 admin；请求体/服务端文件
≤ 256 KiB，单次 ≤ 100 条（scrypt 成本线性）。导入的用户一律是普通用户。

## 背景

运营场景需要一次导入多个用户（团队 onboarding），逐个在页面添加或 SSH 跑 CLI
都太繁琐。需求明确要求「txt 批量添加，每行一个 用户名,密码」且「支持服务端与
本地两种文件浏览」。D13 刚把用户管理收敛到 admin，导入必须沿用同一权限模型，
同时不能把「web 面读服务器任意文件」这个洞开出来。

## 考虑过的替代方案

- **任意服务端路径输入（文本框填绝对路径）**——否决：等于给 web 面开了任意
  文件读（/etc/passwd、其他应用配置），突破 D13「提权必须过 shell」的边界。
  固定 `imports/` 沙箱目录 + basename 白名单把可读面钉死。
- **multipart 文件上传（req 流直接解析）**——否决：现有端点全部 JSON-only
  （D-UM-2 的 CSRF 论证）；FileReader 读原文走 JSON 上传，同源同策略，浏览器
  侧零额外解析代码，行号在两种模式下一致。
- **逐条跳过坏行、导入其余（best-effort）**——否决：半成功状态难解释
  （哪些进了哪些没进）；all-or-nothing + 行号明细与 writeUsersFile 的原子写
  语义一致，改完文件重传即可。
- **导入时附带 role/disabled 字段**——否决：角色 CLI-only（D13）；禁用账号由
  单个 PATCH 覆盖，txt 格式保持两列最小形态。
- **客户端解析成条目数组再上传**——否决：行号对不上原文（跳行/注释），错误
  明细必须指回原始行号；服务端统一解析是唯一真实来源。

## 为什么这样选

本地模式零服务端文件系统暴露；服务端模式用固定目录换取「服务器上已有的文件
直接导入」的便利，且不引入路径遍历面。all-or-nothing + 行号明细让失败可机读、
可修复、可重传。100 条/256 KiB 上限把 scrypt 总成本压在秒级（libuv 线程池
并行），避免导入变成网关停顿。
