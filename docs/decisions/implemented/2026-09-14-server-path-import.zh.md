# 批量导入改用任意服务器绝对路径（{path}，修订 D14）（2026-09-14）

## 决定了什么

`POST /auth/users/import` 的服务端文件来源从 D14 的 imports/ 沙箱（`{file}` +
GET 目录列举）改为 `{path}`：服务器上任意绝对路径的 `.txt` 文件。沙箱模式
（`{file}` 来源与 `GET /auth/users/import` 列举）一并移除，端点只剩 POST。
保留的纪律：仅 admin；非绝对路径 / 含 NUL / 非 `.txt` 后缀一律
`404 import_file_not_found`（不提供「哪种路径合法」的探测面）；超 256 KiB
→ 413；其余读取失败 → 503；审计日志记录实际路径。页面相应只留「本地文件 /
服务器路径」两种模式。本条修订 D14「任意服务端路径输入被否决」与「固定
imports/ 沙箱」两个决定。

## 背景

D14 把服务端文件来源钉死在 `<usersDir>/imports/` 沙箱（不给 web 面任意文件
读），实际运营中变成摩擦：文件本来就在服务器上，却必须先拷进 imports/。
先是应 owner 要求放开 `{path}` 绝对路径（owner 明确接受 admin 会话可读任意
`.txt`）；放开后沙箱模式沦为冗余入口——两个服务端来源语义重叠，owner 决定
只留更通用的 `{path}`，把沙箱与目录列举一起删掉，端点与页面同步收窄。
可读面仍受三层约束：仅 admin（D13 权限矩阵不变，提权必须过 shell）、`.txt`
后缀（/etc/passwd、users.yaml、应用配置天然排除）、256 KiB 封顶。

## 考虑过的替代方案

- **保留 imports/ 沙箱与 {path} 并存** — 否决：两个服务端来源语义重叠，页面
  与端点各多一份模式分支；{path} 完全覆盖沙箱能力（imports/ 内的文件也能用
  绝对路径指到）。
- **服务器文件系统浏览器（列目录 API + 逐层导航 UI）** — 否决：枚举整个文件
  系统比读单个已知路径暴露面更大，端点与 UI 复杂度都上一个量级；运维场景下
  管理员本来就知道文件在哪。
- **放开任意后缀** — 否决：`.txt` 后缀是廉价的类别围栏，把 passwd/shadow/yaml
  配置等敏感文件挡在端点语义之外，对合法导入零成本。
- **非法路径形态返回 400 invalid_field 而非 404** — 否决：非法形态与不存在
  不加区分，避免端点变成路径合法性探测器。

## 为什么这样选

{path} 以最少入口覆盖全部服务端导入场景：保留原 {file} 流程的校验、上限与
原子写，删掉沙箱目录、basename 白名单与 GET 列举后端点更小；可读面收敛在
admin + .txt + 256 KiB 之内，每次读取落审计日志。本地 {text} 模式不受影响；
无迁移成本（已存在的 imports/ 目录留在磁盘上无害，页面与端点只是不再读它）。
